# Code Review Workflow

Use when reviewing a branch, pull request, local diff, or an explicitly requested organization or standards assessment.

Apply [Work Levels](hands-off-agentic-coding-workflow.md#work-levels) to review and verification effort for the current request. Preserve initial PR completeness review and explicitly requested broad assessments; normal fixups get affected-contract proof and delta review, while rearchitecture covers the whole affected design. A quick tweak requires relevant context and reference reading before editing, then stops without agent-initiated post-edit review, tests, lint, build, or verifier runs. The checks below do not override that stop; independently mandated delivery gates remain separate.

## Intent

**WHY this workflow exists:** Reviews should find concrete bugs, regressions, missing tests, and maintainability risks before style nits.

**WHAT this workflow produces:** Findings ordered by severity, each with a location, risk, and concrete fix. If there are no findings, it says so and names any residual test gaps.

**Decision Rules:**

- Lead with behavior, contracts, data safety, security, and missing verification.
- Configuration diagnostics follow [Safe Configuration Diagnostics](hands-off-agentic-coding-workflow.md#safe-configuration-diagnostics): selective context-approved output and credential status, not broad local env/tool dumps.
- Start from the success condition: name the behavior, invariant, or regression risk that must be proven before judging implementation quality.
- Check whether additional technical capabilities are necessary for the requested outcome using [Solve Real User Needs](../../rules/solve-real-user-needs.md). Do not turn hypothetical scale, extra error handling, or optional robustness into blocking findings or automatic follow-up work. Preserve accepted contracts and demonstrated correctness/security/data-integrity safeguards; this is contextual review, not an automated user-value verdict.
- Use that rule to review the accepted consumer journey, not just the backend: can the actual developer/package consumer discover and activate the feature, reuse/update it, inspect status, and recover through its native surface? Require relevant installed/released behavior evidence where applicable, not wording assertions or an expanded runbook. Preserve a sufficient simple CLI and unavoidable consent/authentication/privilege steps; raise gaps against the accepted outcome, not a second generic UX checklist.
- Review human-facing command output under [Human-Facing Command Reports](../references/guidance-precedence-reference.md#human-facing-command-reports): check information selection and missing-data warnings, not just whether diagnostics are accurate.
- Before revising a policy branch or its expectations, establish whether the accepted behavior is already satisfied. Follow [Verify Existing Behavior Before Policy Changes](hands-off-agentic-coding-workflow.md#verify-existing-behavior-before-policy-changes); preserve an already-correct path and distinguish configuration selection from a genuine semantic change.
- Treat style as worth raising only when it affects clarity, consistency, or future safety. Apply [Contextual Defaults](../references/guidance-precedence-reference.md#contextual-defaults): cite the applicable convention and its scope, honor accepted corrections, and do not turn a generic preference into a finding against a justified contextual exception.
- Use Arrange / Act / Assert comments when each section clarifies meaningful setup, behavior, or assertion. Do not require aliases, no-op setup, or comments solely to manufacture a section; parameterized test arguments already provide arranged inputs.
- Flag cramped adjacent sibling logical blocks when local precedent separates them: top-level functions/classes/modules, class methods, helper sections, and test cases/groups should usually have one blank line between siblings for scanability.
- Use project-local rules first: `AGENTS.md`, `README.md`, `COMMITTING.md`, `bin/README.md`, and local `docs/` docs.
- When a maintainer specifically requests Codex review, use [Requested Codex Reviews](../references/github-tooling-reference.md#requested-codex-reviews) for eligibility, target-repository access, acknowledgment, and current-head completion. This is conditional troubleshooting, not a universal review gate.
- Before editing, read the touched area's closest style/test guidance and sibling precedent. Apply [Organization Before Authoring](hands-off-agentic-coding-workflow.md#organization-before-authoring) when ownership or data flow materially changes. For normal and rearchitecture work, preflight touched conventions a formatter may miss—import grouping, spacing, test hierarchy, naming, and focused assertions—and use the relevant repository formatter/checker. Do not add a post-edit mechanical-check ritual to a quick tweak.
- When exact alignment with a designated implementation is requested, use [Exact Reference Alignment](hands-off-agentic-coding-workflow.md#exact-reference-alignment). Compare source-relative naming, declaration order, whitespace, and wrapping as well as runtime behavior; accept necessary contract adaptations and stronger local constraints, not accidental drift. Formatter success alone does not satisfy the exact-reference request.
- For requested normalization of a related family, apply [Whole-Family Normalization](../references/code-organization-reference.md#whole-family-normalization). Compare every in-scope member's structure, method ordering, return contracts, state transitions, effects, and lifecycle ownership; resolve unexplained differences before accepting completion. Matching names/types or passing tests alone does not establish consistency.
- For production import boundaries, use [Project-Root Imports and Paths](../references/code-organization-reference.md#project-root-imports-and-paths). For Vue component naming and template-ref consistency across analogous in-scope components, structure/root types, form-owned dependent-field watchers, loading/disabled state, stock UI reuse, and scoped utility-style presentation, use the [Vue Component Authoring Reference](../references/vue-component-authoring-reference.md).
- In touched Vue components, check [setup priority and final breadcrumbs](../references/vue-component-authoring-reference.md#setup-priority-and-breadcrumbs), [watcher-local hydration and explicit sources](../references/vue-component-authoring-reference.md#watcher-local-hydration), [record-availability branches](../references/vue-component-authoring-reference.md#record-availability-branches), and [permission-entry/access ownership](../references/vue-component-authoring-reference.md#permission-restricted-navigation-and-access-presentation). Preserve lifecycle order, nil narrowing, pending/error recovery, direct-entry protection, and server authorization.
- In touched Vue components, check [Model Bindings Before Props](../references/vue-component-authoring-reference.md#model-bindings-before-props) separately from SFC block order, and [Mutable Component Workflow Snapshots](../references/vue-component-authoring-reference.md#mutable-component-workflow-snapshots) across capture, restore, and reset paths.
- For transformed prop values, apply [Direct Prop Refs](../references/vue-component-authoring-reference.md#direct-prop-refs): read props inside the computed getter without a derivation-only intermediate ref. Preserve reactive updates, conversion semantics, and refs with independent consumers.
- In touched Vue props and comparable named input declarations, check required-before-optional ordering under [Human Readability](../references/code-organization-reference.md#human-readability) and [Multiline Prop Object Types](../references/vue-component-authoring-reference.md#multiline-prop-object-types). Preserve names, types, defaults, optionality, relative order within each group, positional APIs, and runtime evaluation; do not expand into unrelated declarations.
- For normal/rearchitecture proof and independently required delivery gates, use working project-appropriate linting evidence under [Project Linting Verification](../references/rules-and-verifications-reference.md#project-linting-verification). Reuse applicable evidence, the documented wrapper, and configured warning policy; formatter/typecheck success is not lint evidence. Do not initiate lint after a quick tweak.
- For changed style declarations, follow [CSS Diagnostics for Style Changes](#css-diagnostics-for-style-changes); unrelated changes do not activate CSS-only checks.
- In MJML templates, prefer supported native styling mechanisms over an HTML wrapper added solely for CSS. Use supported direct attributes where available; where a component such as `mj-text` lacks the required attribute, use `css-class` with rules in `mj-style inline="inline"`. Do not invent unsupported attributes or remove structurally necessary wrappers. Run the project's strict MJML validation/compilation, inspect generated inline CSS and preserved content, and verify the relevant rendered behavior. Use [Compiled MJML Output](#compiled-mjml-output) for ending-component and delivered-HTML boundaries.
- For coupled interaction changes or corrective UX feedback across related gestures, use [Interaction Contract Activation](outcome-first-planning-workflow.md#interaction-contract-activation) before the next gesture patch. Keep the fit check scoped to the relevant contract; isolated wording or mechanical changes do not need it.
- When custom code replaces or intercepts a library's interaction lifecycle, use that same interaction-contract check to preserve affected supported input sensors through begin/move/release/cancel. Do not accept native DOM drop handling or mouse-only tests as proof of touch/fallback parity; keep normalization at the sensor boundary and reuse existing domain target/commit rules.
- For disputed UI interaction claims, use [Disputed Interaction Behavior](browser-qa-workflow.md#disputed-interaction-behavior): prefer a focused running-interface experiment with the relevant input before asserting library behavior or recommending upgrades. Distinguish pointer, keyboard, and form paths; source inspection alone is not observed UI evidence, and unavailable runtime evidence does not justify new infrastructure or dependency changes.
- Prefer deletion and simpler existing patterns over new abstractions. Apply [Human Readability](../references/code-organization-reference.md#human-readability)'s per-file cleanup eligibility rule; after an accepted scope correction, inspect the complete in-scope PR for equivalent incidental-only files.
- After feature deferral or simplification, use [Simplification After Scope Changes](../references/code-organization-reference.md#simplification-after-scope-changes): restore the original simple shape when supporting abstractions are no longer needed, remove static reactive wrappers only when the consumer supports plain values, and retain refactors required by accepted work.
- For generic parsing, traversal, tokenization, serialization, or equivalent plumbing, apply [Libraries for Generic Mechanism](../references/code-organization-reference.md#libraries-for-generic-mechanism): inspect existing frontend/backend library choices before adding an overlapping dependency, then compare standard-library, installed, maintained-library, and bespoke options. Prefer lower net owned complexity while preserving runtime compatibility and explicit security policy; sharing a library does not require identical configuration.
- For queued or deferred work, inspect whether its payload references a record the initiating operation deletes or invalidates before execution. Pass immutable delivery fields as a snapshot when they are sufficient; reload live state only when current data is required and absence is handled deliberately. Request a focused delayed-execution or deletion-path check when this lifecycle applies. For persisted argument changes, apply [Durable Job Payload Changes](../references/code-organization-reference.md#durable-job-payload-changes) to type, position, arity, and representation; prove prior payload readability or a verified cutover, not just fresh-producer success.
- For migrations that split or rename persisted settings, map every target setting to its semantically corresponding legacy source before selecting defaults. Preserve existing explicit choices, including opt-outs; use current defaults only when no source setting exists. Request a focused backfill test or data assertion for both an existing opt-out and a missing legacy preference.
- Review migration ownership, order, dialect operations, helper placement, and disposable implementation checks against [Self-Contained Migrations](../references/code-organization-reference.md#self-contained-migrations). Retain check outcomes before removing migration-only checks and dedicated fixtures prior to commit; keep application tests, shared fixtures, and required recovery/audit artifacts. Preserve local definitions, dependency/rollback order, and justified raw SQL; do not rewrite released history or impose a file quota. Review application text rules under [Text Validation Ownership](../references/code-organization-reference.md#text-validation-ownership) and policy-to-service payload typing under [Express Light Rail](express-light-rail-backend-workflow.md#intent).
- For new backfills, apply [Best-Effort Backfills](../references/code-organization-reference.md#best-effort-backfills): tolerate explicitly identified unusable legacy inputs only within the project's preservation contract, retain usable neighbors, and propagate genuine database failures. Require focused valid/malformed/valid and database-failure evidence; verify accepted loss/recovery before source removal, rather than prescribing deletion or rewriting released migrations.
- For frontend request aggregation, use [Keyed Frontend Request Coalescing](../references/engineering-techniques-reference.md#keyed-frontend-request-coalescing) to review canonical keys, result ownership, invalidation, and cancellation separately.
- For expected-JSON consumers and error recovery, apply [Intermediary Responses to JSON Requests](../references/engineering-techniques-reference.md#intermediary-responses-to-json-requests): review marked/unmarked HTML on successful and rejected responses, ordinary JSON/non-JSON contracts, loaded-state and uncertain-write safety, framework propagation, listener teardown, and optional-preview trust.
- When a review finds a dependency capability gap, use [Evidence-Backed Upstream Limitations](../references/engineering-techniques-reference.md#evidence-backed-upstream-limitations) before suggesting private patches or duplicate upstream issues.
- Review development wrappers against [Thin Entry Points and Values](../references/dev-tooling-portability-reference.md#thin-entry-points-and-values): reject unnecessary compatibility parsing, fallback startup, and duplicated environment/configuration helpers while preserving real prerequisite, integration, and lifecycle invariants. Apply [Dependency Release Selection](../references/dev-tooling-portability-reference.md#dependency-release-selection) when choosing an adopted release instead of copying a sibling's incidental pin.
- For validation catalogs and argument preflight, apply [Ownership and Control-Boundary Checks](../references/dev-tooling-portability-reference.md#ownership-and-control-boundary-checks): derive ownership from its existing execution/config source, keep help-like child argv opaque, and request a real spawned-child proof without inventing override features.
- Prefer explicit branching or guards over ternaries when control flow reads more clearly; do not extract wrappers solely to remove ternary syntax. For service inputs, query naming/scopes, comments, preload contracts, CRUD/index naming, field policies, and semantically safe emptiness checks, use the bounded guidance in [Code Organization Reference](../references/code-organization-reference.md).
- Check [Mutually Exclusive Alternatives](../references/code-organization-reference.md#mutually-exclusive-alternatives) for grouped decisions, and [Private Helper Inputs](../references/code-organization-reference.md#private-helper-inputs) for source-value arguments with helper-owned derivations.
- Review canonical text handoffs under [Text Validation Ownership](../references/code-organization-reference.md#text-validation-ownership): trace actual producers before deleting transformations, preserve accepted inputs, and distinguish no-match lookups from required persisted-value invariants. Check verified remote-column comments under [Integration Model Contracts](../references/code-organization-reference.md#integration-model-contracts).
- For partial Sequelize indexes and migration layout, use [Named Partial Indexes](../references/express-light-rail-backend-concepts-reference.md#sequelize-named-partial-indexes) and [Migration Field Groups](../references/express-light-rail-backend-concepts-reference.md#migration-field-groups); preserve database semantics and released history.
- Check positive `is`-prefixed local/computed state under [State Names](../references/code-organization-reference.md#state-names-and-dependency-local-ordering), identity-only [navigation inputs](../references/code-organization-reference.md#ui-navigation-handler-names), and [Guard Clauses](../references/code-organization-reference.md#guard-clauses-and-exceptional-responses) for explicit completeness checks, existing `isNil` when null and undefined both mean absence, and Luxon `isValid` guards when Luxon owns parsing. Preserve polarity, intentional null-only distinctions, accepted syntax, and timezone semantics.
  With existing Luxon, prefer parsed values and explicit output formats over timestamp slicing; retain missing-time distinctions and intended zone behavior.
- Apply [Human Readability](../references/code-organization-reference.md#human-readability) to boolean-selected actions and redundant state staging: prefer named operations and direct simple construction while preserving guards, effects, deferred work, and returned identity. Check [same-name destructuring](../references/code-organization-reference.md#named-helper-results), including one property, without detaching receiver-dependent methods or snapshotting live reactive reads.
- Keep unchanged computed projections source-domain-named through returns and consumers under [State Names](../references/code-organization-reference.md#state-names-and-dependency-local-ordering), preserving null/reactive semantics and meaningful transformation, role, or collision distinctions.
- Distinguish meaningful fixture records from homogeneous repetitions under [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification): prefer named attributes over compression-only tuple setup loops, without banning case tables or changing factory lifecycle.
  For ordinary factory defaults, apply [Varied Factory Defaults](../references/code-organization-reference.md#varied-factory-defaults): existing random generators, valid dependent fields, and explicit scenario values.
  Inline single-use literal `describe.each`/`test.each` tables at the runner call under the same scenario guidance; preserve explicit names/callbacks, types, order, titles, and registration timing. Reused or independently meaningful fixture tables may remain named.
  For integration-model factories and helpers, apply [Integration Factory Ownership](test-factory-traits-and-service-shape-workflow.md#integration-factory-ownership): keep them in test infrastructure under their integration's named bundle and align imports/exports without absorbing application-owned factories.

- Do not block on project-specific rules that are not documented locally.
- Test expectations should be declarative expected data, not expectation-building logic. For business catalogs and configured defaults, prefer explicit expected values over mapping, sorting, branching, or deriving expectations from the same production constant/helper under test.
- Assert fetched/returned collections directly rather than projecting actual values inside `expect`; preserve native async and matcher APIs. Do not add sorting solely to normalize assertions or assume unordered SQL guarantees operation sequence. Distinguish raw fixture `...Attributes` collections from persisted records, including table-driven fields and consumers. Follow [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification) and compliant project siblings.
- Put queries used only to observe persisted results in Assert beside their expectations. Use the normal model API for routine ORM-backed observations, retaining specialized SQL where concrete database semantics require it. Prefer a simple awaited query over unnecessary post-query filtering only when fixture isolation makes it equivalent; preserve needed constraints/options and keep the actual operation in Act. Follow [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification).
- Require exactly one `expect` per non-controller expect-based test as the shared default, without local opt-in. Preserve the explicit controller exception for meaningful direct status/body assertions; use [Assertion Quality Requires Review](../references/test-alignment-verifier-reference.md#assertion-quality-requires-review) for controller path/filename classification, not inference from HTTP usage. Preserve native `node:assert` tests, native promise-error and web-first matchers, and direct comparisons of actual returned objects/arrays. Do not invent a coupled-invariant exemption, move assertions into Arrange/Act/hooks/helpers, fabricate summary objects, bundle `.mock.calls`, or weaken expectations to satisfy count.
  For throws and rejections, prefer independently specified string/regex message matchers over arranged error identity under the same assertion-quality guidance.
- Keep independent saves and other independently meaningful outcomes in separate focused tests. For saves, use API spies with concrete expected payloads rather than `expect.anything()` payloads or bundled call arrays. Preserve required transition, race, and rollback setup and scenario identities in each test that needs them; splitting observations must not discard the causal sequence. Assert important mock interactions directly in their own focused tests using supported native matchers.
- For changed JavaScript/TypeScript test files, read the inherited [Shared Baseline](../references/test-alignment-verifier-reference.md#shared-baseline) before the first push or review, alongside the nearest test-directory README and local test guidance. Apply naming, phase, and shared exactly-one-expect requirements to every test in each changed file, not only edited callbacks; retain explicit local additions and supported scoped suppressions. Report genuine local policy conflicts truthfully. Before merge, obtain the applicable declared check's current-scope result using [Diff Scope](../references/test-alignment-verifier-reference.md#diff-scope); a passing behavioral suite or anticipated final-yield advice is not that evidence. Use the declared [Test Assertion Focus check](../references/test-alignment-verifier-reference.md#semantic-assertion-focus-check) as well: syntax-only `PASS` does not prove semantic assertion quality.
- When the user designates another project as testing precedent, inspect that reference before test edits and reuse its applicable harness and assertions. Follow [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification); do not replace the designated pattern with an unexamined custom renderer or parser.
- For dependency-related tests and cutovers, apply [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification) to distinguish upstream API behavior from application-owned invariants, observed integration regressions, and already-covered consumers before recommending additions or deletions.
- For component tests, apply [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification) to visible application outcomes, scenario-local mount/response setup, shared API-response infrastructure support, typed frontend factories, and readable assertion targets. Before accepting repeated API/configuration/authentication mocks just to vary responses, inspect existing response support; preserve focused collaborator mocks required by the tested contract. Check source/test ownership under [Domain-Oriented Modules and Tests](../references/code-organization-reference.md#domain-oriented-modules-and-tests); preserve legitimate infrastructure and integration assertions without extraction quotas.
  Prefer separate same-URL/query matcher/response definitions over scenario handler dispatch under [Composable HTTP GET Routes](../../examples/factory-traits-and-service-shape.md#query-deferred-and-failure-scenarios); preserve async timing, precedence, failures, and unmatched behavior.
- For permanent test intent and setup, apply [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification): use factories rather than unrelated production-service setup, retaining subject-service and feature-test calls; test the current interaction instead of memorializing a retired control's absence. Preserve legitimate negative contracts and keep investigative probes disposable.
- For asynchronous test mechanics and ongoing suite selection, follow [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification): inspect actual synchronization-helper contracts before manual relay/wait loops, and prefer glob/metadata suite conventions over per-file catalogs while preserving complementary discovery and setup. Retain specialized failure observations and explicit scenario assertions.
- Before proposing test additions, consolidation, or removal, identify the uncovered observable behavior or maintained invariant, inspect existing consumer coverage, and weigh setup/runtime/maintenance cost. Prefer cheap exhaustive literal tables for finite pure utilities and representative consumer-facing boundary scenarios for cross-module workflows; retain focused lower-level tests for distinct uncovered risks such as authorization or concurrency. Test layout follows ownership, not a mandatory suite per source file. See [Domain-Oriented Modules and Tests](../references/code-organization-reference.md#domain-oriented-modules-and-tests).
- Pair positive application-boundary coverage with a meaningful rejected/excluded control under [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification). Check that it exposes wrong fixtures or missing filtering/authorization; reuse existing boundary coverage instead of adding unrelated cases or quota-driven duplicates.
- For CLI/API adapter doubles, review whether consumed options, fields, response shape, and semantics match the supported external interface; use [External CLI and API Doubles](testing-instructions-workflow.md#external-cli-and-api-doubles) for focused fixtures and safe boundary smoke decisions.
- For tooling verification, review whether an appropriate established suite exists before accepting a new permanent runner; for one-off no-suite checks, prefer disposable behavioral smoke evidence. See [Hands-Off Agentic Coding](hands-off-agentic-coding-workflow.md#intent) for the scope boundary and permitted permanent regression/infrastructure work.
- Keep persisted scenario creation explicit in each test's Arrange section, even for identical records; flag persistence hidden in shared `beforeEach` hooks. Preserve legitimate environment hooks and opt-in named factory traits. Keep descriptive fixture-backed test function names, inspect configured runner cleanup before adding redundant local hooks, and retain uncovered-resource cleanup or intentional mid-test restoration. Follow [Scenario-Oriented Verification](../references/code-organization-reference.md#scenario-oriented-verification) and [Cleanup Necessity](../references/code-organization-reference.md#cleanup-necessity).
- Before adding a shared setup or teardown hook that awaits an external, asynchronous, or potentially slow subsystem, assess its fan-out under the configured runner: a global `beforeEach` or equivalent multiplies waits, retries, polling, or cleanup by every test and worker. Keep the hook in the narrowest suite or describe block whose tests observe the asynchronous invariant unless every test needs it. Preserve a focused regression for the race or lifecycle hazard. Reviewers should reject global asynchronous cleanup without an all-suite correctness reason or measured fan-out rationale; this does not constrain normal in-memory setup or impose timing budgets.
- Before retaining or moving test cleanup, identify the live resource, isolation requirement, or observable invariant that needs it. Remove unnecessary settlement of intentionally pending in-memory mock promises rather than moving it into `finally` or a hook for body shape; do not resolve early, snapshot, or weaken a pending-state assertion. Reuse automatic teardown. Keep explicit disposal for live timers, I/O, subscriptions, disposal-under-test, or demonstrated isolation needs; see [Cleanup Necessity](../references/code-organization-reference.md#cleanup-necessity) for examples.
- Check [Cleanup Necessity](../references/code-organization-reference.md#cleanup-necessity) for invariant wrapper teardown: register it once in runner-loaded shared setup, migrate duplicate per-file registrations together, and place setup registrations before teardown registrations for source readability—not as a claim about changing runner phases. Preserve disposal-under-test and uncovered cleanup.
- For generated or touched JavaScript/TypeScript, allow short clear one-line guards with a blank line afterward; consecutive short guards may be adjacent with a blank line only after the last. Keep non-short guards multiline and braced; do not compress every guard. Prefer `isUndefined` only when Lodash is already available and undefined-only semantics fit; preserve safe `typeof` checks, nil semantics, local/user precedence, and do not add dependencies. For exceptional error responses, use an explicit early return and keep the ordinary error response as the normal path. Elsewhere, prefer explicit branching when clearer; a concise scalar ternary may remain when genuinely clearest. See [Guard Clauses and Exceptional Responses](../references/code-organization-reference.md#guard-clauses-and-exceptional-responses).
- Make readability an explicit delivery gate: before reporting `PASS`, name each independent responsibility and its side effects. Flag unstructured accumulation of independent scenarios or repeated mechanics that hides the contract; review structure rather than numeric readability proxies, preserve literal scenario data locally, and do not require mechanical splits or generic fixture builders. Use the scenario guidance in [`code-organization-reference.md`](../references/code-organization-reference.md) when reviewing verification code.
- For input-heavy utility tests, selectively consider reproducible property-based or metamorphic checks; use the bounded mutation spot-check only when test sensitivity is uncertain. Follow [Input-Heavy Utility Tests](../references/code-organization-reference.md#input-heavy-utility-tests) and [Bounded Mutation Spot-Checks](../references/code-organization-reference.md#bounded-mutation-spot-checks), not exhaustive business matrices or numeric quality gates.
- When modeling mutually exclusive states, consider a discriminated union rather than independent flags; see [Tagged Unions for Exclusive States](../references/code-organization-reference.md#tagged-unions-for-exclusive-states). Do not replace runtime validation at untrusted boundaries.
- For each changed barrel or `index.ts`, use the applicable semantic groups and ordering before alphabetizing. Apply the CRUD/controller-order exception and group labels in [Service Orchestration Readability](../references/code-organization-reference.md#service-orchestration-readability); alphabetize other exports within their groups. Keep namespace imports, named exports, and default-export object keys aligned with that applicable order, preserving initialization-sensitive behavior. Flag deviations from the actual convention, not from a blanket alphabetical rule; do not require unrelated barrel rewrites. For test dependency bundles versus direct full-module subject imports, use [Project-Root Imports and Paths](../references/code-organization-reference.md#project-root-imports-and-paths).
- Review commit scope when relevant: flag mixed code/test changes, migrations/schema/data changes, dependency churn, formatting, and documentation or workflow-learning updates unless the user explicitly requested a combined commit and the files are inseparable for review.
- For maintainability or organization findings, use `docs/references/code-organization-reference.md`: flag boundaries, modules, helpers, or abstractions only when they affect ownership, data handoffs, dependency direction, side effects, or future change safety. Keep complexity checks separate from ownership and safety findings.

- Before proposing a reorganization, run the domain-discovery checkpoint in [`docs/references/code-organization-reference.md`](../references/code-organization-reference.md): inspect topology, cohesive concepts, repeated change clusters, varying dispatch dimensions, owned invariants, dependency direction, and sibling conventions. Treat churn, growing branches, context-heavy helpers, and repeated boundary crossings as evidence to investigate—not proof of a new abstraction—and record each candidate's evidence, responsibilities, boundary, and smallest safe next action.
- Flag private helpers that read instance fields when a caller can pass those values explicitly. Do not force parameters when the helper is inherently bound to object state. For service classes, apply the conventions linked above: constructor-backed action inputs stay in `perform`, developer preload guards precede side effects, and returned instances preserve caller preload graphs.

## Organization Assessment Scope

Use this procedure when the request explicitly includes assessing code organization or compliance with project standards, including during improvement or simplification. The **assessment boundary** is the area the user asked to evaluate; the **delivery scope** is the bounded change selected afterward. Do not silently reduce the former to the latter, or turn an ordinary small task or diff review into a repository-wide audit.

1. Name the requested area and its relevant modules, public entrypoints, local rules, and exclusions. Resolve its boundaries from the request and project evidence; identify genuinely unresolved scope rather than implying whole-project coverage.
2. Read the complete in-scope implementation modules, their public-export paths, and the related type owners and callers needed to understand ownership. Apply this workflow's existing criteria and the [Implementation File Boundaries](../references/code-organization-reference.md#implementation-file-boundaries) and domain-discovery guidance. Trace responsibilities, state and side effects, initialization ownership, and dependency direction; check local import/export conventions as well as runtime behavior. Passing tests or formatting does not establish this structural coverage.
3. Before selecting a change, record each material finding with its location, governing rule, concrete ownership or maintenance risk, and disposition: selected for delivery, deferred with a reason, already covered, or unresolved pending named evidence. Keep hypotheses distinct from supported findings. Name unassessed files or boundaries and missing evidence; they are not clean results. Use the existing review/session record, not another inventory or automatic issue-filing campaign.
4. Select the smallest coherent delivery under the calling workflow. Preserve public contracts, precise types, supported imports, shared initialization, and behavior. At closeout, distinguish corrected findings, remaining findings and their next action, and unassessed scope. A successful bounded fix is not a clean assessment of the remaining area.

For example, a factory facade that also implements context lifecycle, association handling, and attribute construction needs an ownership review of those responsibilities and any shared adapter state. If the package barrel obtains unrelated errors, constants, and types through that facade, assess that export coupling too. Moving adapter recognition policy alone does not dispose of either concern; record any deliberate deferral and preserve supported root imports when proposing a split.

Conversely, parsing, validation, and formatting functions that serve one cohesive value contract may remain together. Several functions or classes, file length, and a generic SOLID label are not sufficient reasons to split a module; show the actual ownership or change-boundary problem.

## Documentation Purpose and Placement

For changed documentation, read the applicable ordinary-language project rules and identify the intended reader question, purpose, placement, and existing authoritative owner. Apply [Selecting Documentation Content](project-knowledge-base-workflow.md#selecting-documentation-content); assess the passage's content, not just its pathname.

Source-directory READMEs may teach when and why to use a layer or pattern, how to author within it, and its boundaries, with small usage examples. Flag passages that merely inventory implementation behavior or repeat another layer's instructions. Identify the affected passage, governing rule, and concrete correction: explain the authoring decision, link to the existing owner, or retain implementation-local rationale beside code. Use the knowledge base for an actual durable domain or architecture question, not as a destination for displaced implementation summaries. Do not ban source READMEs or force new documentation when an existing owner already answers the question.

Use the actual diff to find changed source-directory README passages, then compare each proposed paragraph with the project's documentation-purpose rule and its existing owner before reporting review completion. Check mixed passages sentence by sentence: legitimate layer-boundary advice does not make an adjacent event-field catalog or client reconciliation description appropriate. A finding must cite the concrete passage and governing rule and name the existing owner or smallest correction, not merely repeat the general policy. Keep this evidence in the existing review record; do not create a documentation inventory or claim an automated verifier assessed the passage without an observed result.

Compare material documentation claims with current implementation and supported configuration, including execution order, parallel prerequisites, retries versus reruns, partial failure, and the meaning of success when relevant. Recover referenced implementation and existing owner documents into the semantic request before assessment; unavailable required evidence is `BLOCKED`, not approval based on formatting, links, or author assertions.

The supplied `marlens-rules:documentation-purpose-alignment` contract selects changed root/nested Markdown and MDX through OMP Verifier. Assess the complete changed passages and governing guidance with cited whole-scope results; a clean subsection or empty selection does not establish semantic coverage. The provider supplies policy, while Verifier owns capture, evaluation, and native blocker delivery; this contract does not add a hard completion veto or unattended reassessment.

For main README capability and usage claims, apply the [released-artifact boundary](release-notes-workflow.md#shared-release-history-default). An `Unreleased` label does not make a source-only capability preview appropriate in the main README.

Report documentation-purpose coverage separately from formatting, link validity, behavioral tests, and code-module verification; none proves the others. If the required rules or source are unavailable, name the missing prerequisite rather than claiming semantic coverage. Exercise the contrasting [documentation-purpose examples](../../examples/documentation-purpose-review.md) when verifying this review path.

## CSS Diagnostics for Style Changes

When style declarations change, inspect the project's configured CSS diagnostic provider for the changed standalone CSS files and supported embedded Vue `<style>` blocks, in addition to formatting, type checks, and rendered behavior. A Vue script/template-only change or another unrelated change does not acquire CSS-only verification work.

`css(vendorPrefix)` identifies a CSS language-service diagnostic. Establish coverage from the project's actual linter/parser/plugin/provider configuration and output: ESLint can support additional languages through suitable integrations, but a script-only ESLint, type-check, or browser PASS does not establish that CSS diagnostics are clear. Add supported standard equivalents where appropriate while retaining browser-required vendor-prefixed fallbacks; for example, supported `line-clamp: 3` can accompany `-webkit-line-clamp: 3`. Do not require an unprefixed twin for every prefixed property.

Reuse project-configured tooling and respect its supported syntax, dialects, custom CSS data, and settings; validate embedded style blocks with their supported service rather than parsing the entire Vue file as CSS. Report unavailable required diagnostic coverage as `BLOCKED` with the missing provider or block/dialect support. Do not silently add project dependencies, weaken checks, or substitute rendered behavior for diagnostic evidence.

## Compiled MJML Output

MJML ending components such as `mj-text` can treat their contents as HTML. Nesting another MJML component there, such as `mj-raw`, does not guarantee it is compiled away; strict compilation and a plausible browser preview can still leave literal component elements in delivered HTML. Validate the supported hierarchy and prefer direct interpolation of already-sanitized HTML where supported. Preserve escaping, sanitization, and structurally necessary wrappers.

Inspect the resulting DOM at the affected boundary for leaked component elements while preserving intended paragraph breaks, formatting, links, and inline whitespace styles. Distinguish actual elements from escaped user-visible text; do not add a blanket substring verifier or ban all wrappers. Keep strict-compilation, browser-preview, and actual email-client compatibility evidence separate; none alone proves the others.

## Process

1. Read the request, issue, PR body, or plan.
2. Inspect the in-scope files: the changed files for a diff review, or the declared area under [Organization Assessment Scope](#organization-assessment-scope). Identify whether the work is backend, frontend, migration, test-only, documentation-only, or cross-cutting.
3. Read project-local rules and setup docs that govern the assessed area.
   For documentation changes, perform [Documentation Purpose and Placement](#documentation-purpose-and-placement) before reporting review completion.
4. Check behavior and contracts: API shapes, serializers, policy/access rules, migrations, persistence, and UI route flows when relevant. Apply [Invariant-Preserving Mutations](../references/code-organization-reference.md#invariant-preserving-mutations): ordinary operations preserve their invariant and unrelated valid state rather than invoking general repair; retain explicitly required repair/migration work.
   For live resource-update channels, apply [Resource-Change Notifications](../references/code-organization-reference.md#resource-change-notifications): retain authorized delivery and sufficient decision metadata, keep full representations on the authorized read path, and compare notifications with observed saved state before refreshing.
   In backend rails using `IndexSerializer`/`ShowSerializer`, review [Serializer Selection by Action](../references/express-light-rail-backend-concepts-reference.md#serializer-selection-by-action): index endpoints own the index representation; ordinary show/create/update responses own the show representation, even when their fields currently coincide. Preserve deliberate operation-specific contracts.
   Apply [Serializer Field Allowlists](../references/express-light-rail-backend-concepts-reference.md#serializer-field-allowlists) to unchanged same-name fields using the existing pick utility, preserving explicit conversions, relationships, and the complete response contract.
   For existing class-based families, review [Existing Class-Based Serializer Dispatch](../references/express-light-rail-backend-concepts-reference.md#existing-class-based-serializer-dispatch): prefer supported collection entrypoints over equivalent caller-side maps, retain meaningful transformations, and verify inferred constructor arguments and the target's error, preload, async, and empty-array contracts before adopting dispatcher changes.
   Review [Model Collection Queries](../references/express-light-rail-backend-concepts-reference.md#model-collection-queries): reject thin custom finder wrappers and whole-source materialization for potentially large synchronizations. Check the installed batching contract, complete filters/includes/order, processing across batch boundaries, and preserved failure/transaction behavior. Distinguish bounded source loading from response accumulation; retain meaningful model behavior and genuinely bounded reads.
5. Check type and error handling: avoid unsafe casts, non-null assumptions, swallowed errors, and impossible states represented as runtime branches. Apply [Known Application Types](../references/code-organization-reference.md#known-application-types) to annotations and assertions that erase available domain contracts; preserve valid dictionaries and unknown input awaiting validation. Apply [Error Ownership and Local Recovery](../references/code-organization-reference.md#error-ownership-and-local-recovery) for transport/UI separation, positive local handling, application error hierarchies, and operation-specific structured logs.
6. Check tests and verification at the current work level: normal and rearchitecture work need the smallest meaningful proof of the affected contract; reuse unchanged evidence. PR testing instructions should match user-visible behavior. A quick tweak does not trigger post-edit checks.
7. Report evidence-sensitive checks as `PASS`, `FAIL`, or `BLOCKED` using the shared vocabulary in `AGENT_RULES.md`.
8. Check code organization: flag modules, services, repositories, value objects, adapters, or helper extractions that obscure ownership, create cycles, pass context bags, hide side effects, or fail to group code that changes together. Treat an oversized file as a signal to inspect responsibility clusters, independent change axes, side effects, dependency direction, and extraction seams; do not require a split when the file is cohesive, and do not accept a mechanical split that preserves the same tangles. State names should describe represented domain facts or lifecycles, and query/composable results should stay beside their direct derived state unless a stronger local convention applies.
   Apply [Service Runtime Exports](../references/code-organization-reference.md#service-runtime-exports) and [Integration Model Contracts](../references/code-organization-reference.md#integration-model-contracts): check service modules for separately exported runtime helpers/errors, verify external contracts live with their integration, and distinguish independently named model files from cohesive supporting types. Trace affected consumers to the owning modules and reject duplicate declarations or compatibility re-exports left behind by a move; preserve stronger local conventions and existing contracts.
9. Check simplicity: flag helpers, options, abstractions, comments, or compatibility paths that solve no current problem. Apply [Default-Safe Lifecycle APIs](../references/code-organization-reference.md#default-safe-lifecycle-apis) when ordinary safety is opt-in or implementation bookkeeping leaks into a framework-like caller interface.
10. Check dead code: if a replacement makes old code unreachable, remove stale types, imports, exports, and documentation.

## Comments in the Maintainer's Voice

For human-facing PR comments written in the maintainer's voice, state the concern and a concise direction. Retain concrete behavioral risks and why they matter; cut unsolicited helper signatures, parameter lists, guard clauses, intermediate variable names, and step-by-step implementation designs. Keep that detailed analysis in the existing review evidence unless the maintainer asks to include it.

- **Readability:** “Could we extract this into a function? The conversion logic makes the submit handler difficult to follow.” Suggest the useful boundary without designing the function's internals.
- **Correctness:** “Falling back to the browser's timezone could save the wrong cutoff for someone in another timezone. An invalid conversion could also reach the save request. Could we keep the configured timezone and reject invalid values before saving?” Preserve the risk explanation rather than reducing the comment to “fix the timezone.”

These examples illustrate comment scope, not findings to paste without evidence. This preference does not limit technical investigation, full review reports, or explicitly requested implementation suggestions.

## Optional Selected-File PR Review and Viewed State

Use this mode when the request names a pull request and one or more repository-relative changed paths. Confirm the GitHub API identity is the intended account. Reuse the review process above, inspecting enough PR/base, relevant source, caller/test, and project-local context for each selected file; record the exact reviewed `headRefOid` and focused verification.

Only when explicitly requested, mark a selected file viewed if it has no finding and sufficient review evidence. Do not mark files with findings, missing relevant context, unresolved verification, or absent exact paths. Follow [Pull Request File Viewed State](../references/github-tooling-reference.md#pull-request-file-viewed-state): require the current head to match the reviewed OID immediately before the mutation, then freshly read back both the head and exact file's viewed state. Claim success only for a matching head and `VIEWED`; changed heads require fresh review, not a stale success claim. These checks are not an atomic revision-conditioned mutation.

Report selected paths, reviewed revision, findings or verification limits, and observed viewed state. Keep mutation/readback failures separate from review conclusions. Viewed state records personal progress, not PR approval or merge readiness; this mode does not authorize source edits, commits, pushes, approval, merge, or marking unrelated files.

## Output Contract

List findings first, ordered by severity.

```text
[severity] Short finding title
File: path/to/file.ts:42
Risk: What can break or mislead users/developers.
Fix: One concrete change.
```

After findings, include open questions or assumptions. If there are no findings, say that clearly and mention any test gaps or residual risk.
