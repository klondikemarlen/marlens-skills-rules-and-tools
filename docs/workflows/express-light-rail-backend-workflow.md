# Express Light Rail Backend Workflow

Use when adding or changing a backend feature in a Node.js + Express + TypeScript project that follows the light-rail shape: route, controller/handler, policy/auth check, service/use case, serializer, model/data access, and focused tests.

## Intent

**WHY this workflow exists:** Several projects use the same backend feature rails. Centralizing the shape avoids re-copying WRAP-specific docs while keeping the workflow generic enough for Express projects with different ORMs, auth middleware, and test factories.

**WHAT this workflow produces:** A scoped backend slice wired through existing project rails, with explicit auth, validation, response shape, persistence, and verification.

**Decision Rules:**

- Project-local docs, wrappers, model conventions, auth context, error middleware, and factory helpers win.
- Use `docs/templates/backend/express-light-rail/` as the starting point when the project has no closer local template.
- Keep controllers thin: request parsing, policy-scoped ordinary reads, status codes, and response shape; delegate domain decisions and nontrivial orchestration.
- Where the controller architecture uses single-record loaders, prefer an awaited named controller-local helper such as `const workflow = await this.loadWorkflow()`. Preserve lookup predicates and required association preloads inside the loader, returning the record or null; keep 404/403 decisions explicit in the public action. This does not require a service/repository/base-controller abstraction or move ordinary collection reads. See the [controller-local loader example](../templates/backend/express-light-rail/controller-template.md#controller-local-record-loading).
- Keep HTTP failure handling visible in the public action or established error boundary under [Error Ownership and Local Recovery](../references/code-organization-reference.md#error-ownership-and-local-recovery). Required-result service failures propagate by throwing; format-specific helpers prepare successful content, not separate HTTP errors from failure-only sentinels. Normally finish fallible preparation before success headers; the explicit [quick-start download contract](../templates/backend/express-light-rail/controller-template.md#quick-start-download-responses) instead interrupts failed transfers after headers. Preserve valid empty/optional results and existing error/status contracts.
- For HTTP responses and persisted status shown later, apply [Internal Errors, Public Messages, and Logs](../references/code-organization-reference.md#internal-errors-public-messages-and-logs): select a safe operation-specific message at the existing public boundary and keep authorized debugging context separate from both the public message and the sanitized log.
- Pass policy-filtered request attributes directly to services without controller-side `as` assertions to force compatibility. Fix mismatches in the owning policy/service attribute contracts while preserving filtering, authorization, and the established controller shape; this is not a ban on unrelated TypeScript assertions or a mandate for a particular ORM generic.
- For create-only request fields, use [Action-Specific Permitted Attributes](#action-specific-permitted-attributes): inspect the existing create/update policy allowlists before adding a model validator, while retaining independently required direct-write invariants.
- For matching controllers, import their own services directly from the supported domain barrel, for example `import { IndexService } from "@/services/child-care-spaces"` and `IndexService.perform(...)`. Cross-domain calls and real name collisions retain meaningful namespaces under [Project-Root Imports and Paths](../references/code-organization-reference.md#project-root-imports-and-paths); do not forbid namespace imports universally.
- Put reusable or multi-step domain work in a service/use-case. A policy-scoped ordinary collection query may stay in the controller: standard filtering, distinct joined counts, ordering, pagination, and serializers do not force an `IndexService`. Keep meaningful business logic and nontrivial orchestration in services; choose that boundary before applying established service naming. Follow [Service Orchestration Readability](../references/code-organization-reference.md#service-orchestration-readability), preserving query/transaction semantics and explicit local architecture.
- Under that service lifecycle, keep construction assignment-only and validate required canonical input at action entry before effects. Trace producer-owned normalization rather than silently repairing rejected input in the constructor.
- For model collection reads, follow [Model Collection Queries](../references/express-light-rail-backend-concepts-reference.md#model-collection-queries): prefer supported query APIs over thin custom finders, and use supported incremental traversal for potentially large synchronizations. Preserve complete query options, traversal and transaction semantics; report remaining result accumulation without claiming constant-memory operation.
- For offset pagination, let the request owner resolve the page and pass only the computed `limit` and `offset` into the query. A dedicated query-options object is fine if it contains only consumed fields; narrowing the type of a controller object does not remove its extra properties at runtime. Keep existing cursor contracts. Expose page metadata in the collection response only when its contract calls for it, not as input to each record serializer.
- When inherited collection statics are missing, inspect runtime inheritance and static-type erasure at policy/service boundaries under [Model Collection Queries](../references/express-light-rail-backend-concepts-reference.md#model-collection-queries), then call the concrete or authorized scoped model directly. Preserve legitimate supported rebinding.
- Start required write or snapshot transactions through the [established database entry point](../references/express-light-rail-backend-concepts-reference.md#database-transaction-entry-point), retaining scoped queries, options, callback/error semantics, and transaction propagation.
- Where controller helpers own request-query composition, keep default ordering and required tie-breakers in [the controller ordering helper](../references/express-light-rail-backend-concepts-reference.md#controller-owned-request-ordering). Pass the resolved order to services unchanged, preserving client precedence and stable traversal.
- Authorize and validate before mutation. Fail closed when a policy is unclear.
- Keep [independent permission decisions](../templates/backend/express-light-rail/policy-template.md#independent-permission-decisions) explicit, even when two actions have the same short guards today.
- Name the attempted action and resource in authorization denials: list/view for reads and create/update/delete for mutations, not generic "manage" wording. Add useful parent context only when safe to disclose, for example "You are not authorized to list invoices for this travel request". Preserve policy checks, denial statuses, and deliberate not-found or generic responses that conceal resource existence; never expose private identifiers or internal policy details for clarity.
- Distinguish required validation from optional defensive request-value guards. When the accepted controller pattern forwards input to an existing service/model boundary, pass it unchanged and let malformed input fail naturally through that operation and established error handling. After a maintainer rejects normalization and a replacement guard under a caller-owned formatting contract, remove the guard and its obsolete contract test rather than adding fallback checks downstream. Preserve independently required validation, domain invariants, authorization, attribute filtering, safe query bindings, and service errors. See the [input handoff example](../templates/backend/express-light-rail/controller-template.md#resource-imports-and-query-guards) and [Text Validation Ownership](../references/code-organization-reference.md#text-validation-ownership).
- Keep text normalization and format/character validation in the existing service/model owner, following [Text Validation Ownership](../references/code-organization-reference.md#text-validation-ownership). Preserve relational constraints, required migration cleanup, and accepted normalization-versus-rejection behavior.
- Trace actual producers before removing downstream text normalization: fix the established owner if necessary, test the canonical handoff, then reuse the canonical value unchanged. Keep consumer validation and separately owned external boundaries. Under the same text guidance, accepted unmatched lookup strings return no matches without speculative grammar assertions; required persisted-value invariants and source failures remain enforced.
- Preserve verified remote-column references beside normalized integration attributes under [Integration Model Contracts](../references/code-organization-reference.md#integration-model-contracts).
- Follow [Named Partial Indexes](../references/express-light-rail-backend-concepts-reference.md#sequelize-named-partial-indexes) for stable named decorators with migration-matched database names. Apply [Migration Field Groups](../references/express-light-rail-backend-concepts-reference.md#migration-field-groups) to new or actively reviewed unreleased Knex migrations: ordinary columns (including FK types/nullability and JSON), lifecycle timestamps, then table-level references, unique indexes/constraints and other constraints, separated by blank lines. Preserve schema semantics and released history; use scoped-readability review for inline references/uniques and misplaced constraints.
- For simple one-off cleanup, show the affected tables, row predicates, and write order in the migration entry point under [Self-Contained Migrations](../references/code-organization-reference.md#self-contained-migrations).
- For Knex/PostgreSQL partial uniqueness and SQL literals, use [Knex PostgreSQL Partial Unique Indexes](../references/express-light-rail-backend-concepts-reference.md#knex-postgresql-partial-unique-indexes): preserve index-versus-constraint rollback, installed-version predicate behavior, SQL markers, and application-data bindings.
- For validation-only cross-field rules, use normal model validators or the established service validation boundary under [Text Validation Ownership](../references/code-organization-reference.md#text-validation-ownership), not a new pre-validation hook. Preserve model-owned direct-write enforcement and valid/optional/invalid/asynchronous behavior; genuine lifecycle side effects retain their owner.
- For Sequelize models, apply [Sequelize Model Decorators](../references/code-organization-reference.md#sequelize-model-decorators): omit only proven-redundant argument-free `@Table` declarations and their unused imports; preserve option-bearing or runtime-required decorators.
- Apply [Model Key Declaration Order](../references/code-organization-reference.md#model-key-declaration-order) when declaring persisted model fields: primary key, actual foreign keys, then ordinary fields. Inspect the schema or ORM relationships; leave association declarations separate.
- Follow [Create-Service Input Boundaries](../references/code-organization-reference.md#create-service-input-boundaries): put required positional parent context first, derive dependent facts from the authorized selection, and apply one outer `Partial` when the entire model-backed payload is intentionally partial. Keep simple service-owned input guards before the transaction and consistency-dependent checks within it.
- Pass optional nullable creation fields directly only when model/database evidence proves omission already persists the accepted NULL value; retain meaningful null transformations and omission/default distinctions. Follow the example and persisted-input checks in [Create-Service Input Boundaries](../references/code-organization-reference.md#create-service-input-boundaries), preserving required guards, supported optional fields, and PATCH semantics.
- For service write attributes, prefer an explicit field list for several unchanged same-named inputs when it preserves the write contract. Follow [Service Write Field Projections](../templates/backend/express-light-rail/service-template.md#service-write-field-projections) for existing `pick` usage, service-owned values, and omission semantics.
- For required-new versus reuse-intended lifecycles and conditional Sequelize 7 managed transaction context, use [Service Orchestration Readability](../references/code-organization-reference.md#service-orchestration-readability): keep strict creation distinct from an explicit owning-domain ensure service, and verify propagation and nested reuse before removing transaction parameters.
- For accepted application-wide update-return defaults, use the existing database-client owner under [Service Orchestration Readability](../references/code-organization-reference.md#service-orchestration-readability). Prove installed ORM/production-dialect support and preserve explicit overrides, instance/bulk results, and affected-count contracts before removing redundant service options.
- Serialize explicit fields. For unchanged same-name fields, prefer the existing utility's picked allowlist under [Serializer Field Allowlists](../references/express-light-rail-backend-concepts-reference.md#serializer-field-allowlists); keep conversions and relationships explicit. Do not leak raw ORM/model objects unless that is already the project contract.
- Before adding or replacing a query or response projection, apply [Consumer-Driven Field Selection](../references/express-light-rail-backend-concepts-reference.md#consumer-driven-field-selection). Trace what the actual consumers need and preserve ordering, pagination, and accepted representations.
- Distinguish ordinary response serializers from [dedicated sync conversion serializers](../references/express-light-rail-backend-concepts-reference.md#serializer-model-ownership). The latter own complete source-to-target attribute conversion with existing caller context; services retain queries, transactions, persistence, and orchestration, not a second mapping.
- Spell explicit scalar response fields with their actual [wire primitives](../references/express-light-rail-backend-concepts-reference.md#explicit-scalar-response-types), retaining local-model `Pick` projections and meaningful branded, union, or generic relationships.
- For human-facing server-generated reports, use [Human-Facing Report Formatting](../references/express-light-rail-backend-concepts-reference.md#human-facing-report-formatting): attribute-based private formatters, named formatted results, direct unchanged fields, and existing domain/service computation owners. Preserve nil/zero and presentation contracts; ordinary machine-facing API serializers do not inherit report display formatting.
- In rails using `IndexSerializer`/`ShowSerializer`, reserve the index representation for index endpoints and use the show representation for ordinary show, create, and update responses. Follow [Serializer Selection by Action](../references/express-light-rail-backend-concepts-reference.md#serializer-selection-by-action); preserve deliberate operation-specific contracts and existing response fields.
- For existing class-based families, follow [Existing Class-Based Serializer Dispatch](../references/express-light-rail-backend-concepts-reference.md#existing-class-based-serializer-dispatch): reuse supported collection dispatch instead of equivalent caller-side maps or static-only bypasses. When changing the dispatcher, prove constructor-tuple inference and preserve target-specific sync/async, empty-input, context, and error contracts without per-record argument-tail copies.
- For operation-specific responses, use [Primary Operations and Local Implementation](../references/code-organization-reference.md#primary-operations-and-local-implementation): prefer a flat operation-named serializer over a folder wrapping one representation, retain existing type/alias conventions and meaningful namespaces, and preserve ordinary index/show contracts and response fields.
- For clone-for-creation payloads, apply [Cloning for New Persisted Records](../references/code-organization-reference.md#cloning-for-new-persisted-records) to both allowlists and caller composition: exclude source primary identity, retain legitimate association IDs, and distinguish identity-preserving editor snapshots.
- For response association loading and partial updates, apply [Service Orchestration Readability](../references/code-organization-reference.md#service-orchestration-readability): prefer supported includes plus owning serializers over manual hydration, and preserve omission of optional replacement inputs rather than deriving them from response associations. Verify dialect/page semantics and explicit replacement/clearing through transport.
- A mutation service returns the record ready for its accepted serializer. Put any necessary response reload at the service's final return step, not in the controller; serialize the returned result directly. Follow [Service Orchestration Readability](../references/code-organization-reference.md#service-orchestration-readability), preserving transaction boundaries, authorized visibility, and required caller preloads. Do not add a reload when the result is already ready or move ordinary show/collection reads into new services.
- For registered Sequelize includes, prefer supported named association selectors over repeating model/alias pairs. Follow [Service Orchestration Readability](../references/code-organization-reference.md#service-orchestration-readability), retaining all query options and removing only now-unused model imports after verifying ORM/dialect equivalence.
- For selected-record data missing from an established detail response, use [Detail Responses and Association Visibility](../references/express-light-rail-backend-concepts-reference.md#detail-responses-and-association-visibility): enrich the owning show response and serializer rather than switching to an index-by-ID workaround. Preserve policy and soft-delete filtering in includes and post-mutation reloads; required associations do not justify exposing deleted records. Genuine collection searches and explicitly authorized recovery views retain their own contracts.
- Use existing dependencies: ORM/query builder, transaction helper, logger, validation, and test factories. Do not add a new framework for the template.
- Keep database/model-aware persistence and locking in the owning service/use case, not generic utilities. For protected work, prefer an intention-revealing `With...` service boundary when it coordinates the action; preserve project persistence and transaction rails.
- Reuse a controller-loaded, authorized model across an action-service handoff when project rails support it. If the existing lock helper can reload a supplied model, refresh it after lock acquisition and before business-state checks. Follow [Service Orchestration Readability](../references/code-organization-reference.md#service-orchestration-readability), preserving transaction, authorization, and association-loading contracts without imposing changes on every ID-taking API.
- For persistence-triggered background work, follow [Thin Persistence Lifecycle Handoffs](../references/code-organization-reference.md#thin-persistence-lifecycle-handoffs): register process-lifetime subscriptions in each owning API/worker bootstrap, keep callbacks thin, and put discovery/processing in the owning service/job rather than a shared base model. A separate initializer cannot install callbacks in another process. Preserve delivery and transaction semantics.
- When sibling models own parent timestamp propagation, follow [Child-Owned Parent Timestamp Propagation](../references/code-organization-reference.md#child-owned-parent-timestamp-propagation): keep touching in the child persistence lifecycle, select supported instance/bulk hooks from ORM/dialect evidence, and verify affected-parent isolation and rollback.
- Follow the controller/resource namespace for its policy, including nested resources that project a parent model. Compose applicable inherited parent authorization inside the resource policy; do not substitute the parent policy for the resource policy or scatter resource visibility rules into a listing service. Inspect local nested-policy patterns and preserve any independently required parent and child checks.
- For parent-dependent writes, use the paired routes and scoped member lookup in [Nested Record Loading](../templates/backend/express-light-rail/controller-template.md#nested-record-loading). Where a class controller already authorizes separate parent and child records, use the record-named policy builders in the same example without moving the permission checks out of the actions.
- When a policy constructs another for delegation, use a [private domain-named builder](../references/express-light-rail-backend-concepts-reference.md#delegated-policy-construction) on that policy; actions invoke its permission check without extra caching or abstraction.
- Fit the controller query types, resource policy scope, and collection service to that resource's model or supported read projection, not a parent model merely relabeled as the child. Reuse parent-access predicates without registering the child policy on the parent model. Inspect existing CRUD patterns; fix the resource boundary rather than adding scope-name overrides to accommodate a mismatch. Preserve shared registration/consumer constants. This does not mandate a new table, SQL view, or universal schema.
- For collection endpoints, including projected/picker resources, inspect sibling request-query helpers. Compose established filter scopes with the resource policy and pass request where conditions to that scoped query: client filters narrow, never replace, authorization. Do not introduce arbitrary query support outside the local contract. Verify combined filtering and an attempted selection outside policy visibility.
- When a current caller needs a collection-wide aggregate, use [Optional Collection Summaries](../references/express-light-rail-backend-concepts-reference.md#optional-collection-summaries): keep the same authorized/filtered population without pagination, enforce aggregate-field permissions, and carry typed collection state to its UI consumer. An ordinary list without that need remains unchanged.
- When a derived collection needs distinct values from potentially many persisted parent rows, prefer database-side projection, splitting/aggregation, deduplication, and ordering over loading every parent's values and hydrating ORM instances for application-side aggregation. Selecting fewer columns does not bound row count. Apply authorization and supported filters in the source query; use a raw query or supported read projection following local conventions. Do not mandate normalization, a new table, or a view solely for this optimization; schema normalization is a separate evidence-backed modeling decision.
- For boolean guards over persisted state, use [Database-Side Existence Guards](../references/express-light-rail-backend-concepts-reference.md#database-side-existence-guards): express the complete predicate in one parameterized existence query instead of loading candidate rows solely for application-side filtering. Preserve scope and transaction contracts; retain legitimate record loading and supported ORM queries.
- Before adding a resource picker or collection service, inspect neighboring domain inputs and collection endpoints. Compose an owning-domain input when existing resource-input components own fetching, loading/error state, and autocomplete rendering; keep model bindings and contextual hints in the parent. Follow the established collection-service bundle and naming, including nested `IndexService` conventions where present, rather than introducing a flat `List<Resource>Service`. Preserve selection, visibility-triggered loading, errors, and authorization. Do not add wrappers for trivial controls or impose a universal layout.

## Action-Specific Permitted Attributes

Inspect the existing policy before adding a model validator for request editability. A create-only request field belongs in the create allowlist and not the update allowlist. For example, under an existing `pick`-based policy:

```typescript
permittedAttributesForCreate() {
  return pick(this.attributes, [
    "fundingPeriodId",
    "name",
  ])
}

permittedAttributesForUpdate() {
  return pick(this.attributes, [
    "name",
  ])
}
```

Use the project's actual policy API and authorization checks; the names above illustrate the action boundary, not a new policy base. Both controller actions pass only their action-filtered attributes to the service. Do not merge the raw request back into that payload or replace its type with an assertion.

Regression scenario: create an authorized record in funding period A; submit an update containing funding period B and a changed name; reload the record and prove that its funding period remains A while the permitted name changes. Also retain a successful create proving the field is accepted there. Use the application's actual rejection contract instead if disallowed fields are rejected rather than stripped. Independently required model-owned invariants still protect direct writes: request editability alone does not justify introducing or deleting domain validation.

## Download Filenames

For related download formats, reuse one filename-building function and the consistent layout `<type>, <title>, <date>.<extension>`. Keep title/date preparation shared rather than constructing different layouts per response. Reuse the project's accepted date formatting, filename safety, and header encoding; do not change attachment versus inline behavior or introduce streaming requirements.

For example, with `title` and `formattedDate` already prepared once under that contract:

```ts
function buildDownloadFilename(type: string, title: string, date: string, extension: string) {
  return `${type}, ${title}, ${date}.${extension}`
}

const csvFilename = buildDownloadFilename("Report", title, formattedDate, "csv")
const pdfFilename = buildDownloadFilename("Report", title, formattedDate, "pdf")
```

Both response paths use the same composition and retain their format's extension. Keep the helper local when the concern is controller-local; a shared global utility is not mandatory.

## Download Delivery

When early browser download handoff is explicitly requested, use the [quick-start CSV example](../templates/backend/express-light-rail/controller-template.md#quick-start-download-responses): authorize and filter first, dispatch supported formats explicitly, set attachment headers in a response helper, and pass deferred buffer generation to the shared stream helper. Only CSV with an accepted UTF-8 BOM is supported by this example; do not guess prefixes for PDF, DOCX, or unknown MIME types. Buffered generation with early delivery is not row streaming. Keep existing row-streaming exports streaming.

For download helpers and services receiving an explicit response or writable output, put that parameter first in the helper, service entrypoint, constructor, and callers. Pass it explicitly rather than retrieving the response from hidden instance state. Keep service types at the `Writable` boundary rather than introducing Express coupling; see [Private Helper Inputs](../references/code-organization-reference.md#private-helper-inputs). This is not a universal dependency-order rule.

Choose a canonical example rather than a new npm package here: no maintained package owner or versioned consumer-adoption contract has been established. A package becomes justified only with demonstrated shared consumers and an owner for a typed deferred-generation API, Node writable lifecycle/cancellation, a separately owned Express adapter, releases, and consumer upgrades. Copying WRAP's historical `end()`-then-rethrow failure path is not sufficient: after early delivery a generation failure must destroy the transfer, not complete a partial file.

Verify a real browser's download handoff while generation remains pending, headers and attachment naming, exact final bytes with and without the accepted prefix (including an empty buffer and a near-match prefix), generation rejection, and client disconnect. Observe interrupted transfer rather than normal completion or a JSON error after headers. A generator must honor cancellation for prompt resource release; a transport close cannot forcibly stop an arbitrary promise. Retain authentication, policy filtering, and safe filename/header encoding from the application.

## Process

1. Read the nearest live backend slice for the same area: route, controller/handler, service/use-case, policy/auth, serializer, model, and tests.
2. Pick only the templates needed from `docs/templates/backend/express-light-rail/`.
3. Define the API contract: method, path, params, query/body fields, status codes, response JSON, and error JSON.
4. Preserve independently required request validation using the project's existing style and owner. Where the accepted contract relies on natural downstream failure, forward input through that boundary without adding defensive type/grammar guards in the controller or service.
5. Add authorization before sensitive reads and all writes. For collections, apply the resource policy together with locally supported filter scopes, then pass the established request where conditions to the authorized query.
6. Implement persistence through the project’s existing model/repository/ORM shape.
7. Serialize the response through the project’s response-shaping pattern.
8. Reuse the project's shared HTTP request/test-support helper when one exists, following its contract. Keep authentication real when testing authentication boundaries; do not replace it with a stub or introduce a new wrapper.
   Apply the [controller test shape](../templates/backend/express-light-rail/controller-template.md#controller-test-shape) and [structured query transport contract](../references/code-organization-reference.md#structured-controller-query-inputs) using the actual routing, client, and server parser.
9. Add the smallest runnable test that proves the changed success path and the highest-risk edge. Keep behavioral suites aligned with the source unit they own; follow [Domain-Oriented Modules and Tests](../references/code-organization-reference.md#domain-oriented-modules-and-tests) when a distinct responsibility warrants its own service/use case and matching test file.
