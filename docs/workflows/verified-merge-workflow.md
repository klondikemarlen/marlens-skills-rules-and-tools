# Verified Merge Workflow

## Intent

Shared procedure for [Autonomous Merge](autonomous-merge-workflow.md) and operator [Review and Merge](review-and-merge-workflow.md). The caller owns selection, authority, and the decision to hand back or proceed; this procedure defines the evidence and pinned merge operation. It is not a command or a grant of authority.

## Process

1. **Identify the open target.** Resolve the host, target repository, PR number, base branch and SHA, and head repository, branch, and SHA. Confirm draft state, accepted scope, the applicable project and host requirements, and authority for the intended operation. A closed, retargeted, ambiguous, or unavailable PR is not eligible. Before starting, retrying, or resuming automatic review, confirm live eligibility for those revisions and use the owning checkout. Review-only work needs no checkout mutation. Before fixes, reuse the registered PR-head worktree and apply the [PR workflow](../../skills/pr/SKILL.md) draft-state gate.
2. **Obtain applicable review and verification.** Follow [Code Review](../../skills/code-review/SKILL.md) against the actual base and scope. Require initial complete-PR self-review, applicable checks and QA, and any named reviews required by the request or project. When Codex review is required, follow [Requested Codex Reviews](../references/github-tooling-reference.md#requested-codex-reviews), including eligibility, exact request, acknowledgement, bounded observation or recovery, trusted author, full current-head SHA, comments and threads, and terminal result. A published request, acknowledgement, empty formal review, older result, or silence is not completion. A pending Verifier request needs the named reviewer's next command; pass the still-applicable handle and owning checkout to the verifier, not a file watcher. Skipped, pending, stale, failed, or unavailable results are not passing evidence.
3. **Resolve in-scope findings and refresh evidence.** Use the existing [PR](../../skills/pr/SKILL.md), [Worktree](../../skills/worktree/SKILL.md), and [Commit](../../skills/commit/SKILL.md) procedures for fixes, thread reactions and resolution, and appropriate draft/ready transitions. Record that corrections were required, even if made by someone else. Run affected-contract checks at the current work level, push, and obtain fresh applicable verification, named review, and CI for the exact target, base, and corrected head. Reuse proof only where it still applies; do not reuse a prior revision's verdict as current. Return material product decisions and out-of-scope changes to the maintainer.
4. **Assess all merge gates.** Reconcile unresolved findings, local QA and security requirements, actual human approvals, host protection, required CI, and task and host merge authority. Keep intentional draft status and honor the project's readiness/CI order. A required approval is a gate even if the host does not enforce it. Missing, ambiguous, failed, or stale evidence is not readiness. Do not merge, enable auto-merge, or enqueue while a required result or approval is missing. Report the exact gate; do not change protections, access, credentials, models, or advisor cadence to clear it. A separately authorized disposition under project policy is not a passing result and does not turn this procedure into a waiver.
5. **Reconfirm and pin.** Only when the caller's merge decision and every applicable gate permit it, re-read the live open target, base and head immediately before the operation. If anything changed, reassess and obtain fresh applicable evidence. Prefer the ordinary supported merge path and the project's merge method. Pin to the verified head (on GitHub, use `gh pr merge <PR> --repo <OWNER/REPO> --match-head-commit <SHA>` with the appropriate method where supported). Do not retry unpinned. For a host-required queue, apply the same gates before enqueueing. Override is not part of this procedure.
6. **Read back the result.** Before claiming a merge, read the remote merged state, merge commit, and destination branch. An accepted request, enabled auto-merge, or a queue entry is not a completed merge. The caller owns applicable release, install, and cleanup; preserve verifier handoffs before removing an owned checkout.
