# Code Review Workflow

Use when reviewing a branch, pull request, or local diff.

## Intent

**WHY this workflow exists:** Reviews should find concrete bugs, regressions, missing tests, and maintainability risks before style nits.

**WHAT this workflow produces:** Findings ordered by severity, each with a location, risk, and concrete fix. If there are no findings, it says so and names any residual test gaps.

**Decision Rules:**

- Lead with behavior, contracts, data safety, security, and missing verification.
- Configuration diagnostics follow [Safe Configuration Diagnostics](../hands-off-agentic-coding/workflow.md#safe-configuration-diagnostics): selective context-approved output and credential status, not broad local env/tool dumps.
- Start from the success condition: name the behavior, invariant, or regression risk that must be proven before judging implementation quality.
- Check whether additional technical capabilities are necessary for the requested outcome using [Solve Real User Needs](../../rules/solve-real-user-needs.md). Do not turn hypothetical scale, extra error handling, or optional robustness into blocking findings or automatic follow-up work. Preserve accepted contracts and demonstrated correctness/security/data-integrity safeguards; this is contextual review, not an automated user-value verdict.
- Before revising a policy branch or its expectations, establish whether the accepted behavior is already satisfied. Follow [Verify Existing Behavior Before Policy Changes](../hands-off-agentic-coding/workflow.md#verify-existing-behavior-before-policy-changes); preserve an already-correct path and distinguish configuration selection from a genuine semantic change.
- Treat style as worth raising only when it affects clarity, consistency, or future safety.
- Use Arrange / Act / Assert comments when each section clarifies meaningful setup, behavior, or assertion. Do not require aliases, no-op setup, or comments solely to manufacture a section; parameterized test arguments already provide arranged inputs.
- Flag cramped adjacent sibling logical blocks when local precedent separates them: top-level functions/classes/modules, class methods, helper sections, and test cases/groups should usually have one blank line between siblings for scanability.
- Use project-local rules first: `AGENTS.md`, `README.md`, `COMMITTING.md`, `bin/README.md`, and local `docs/` docs.
- When a maintainer specifically requests Codex review, use [Requested Codex Reviews](../../docs/references/github-tooling-reference.md#requested-codex-reviews) for eligibility, target-repository access, acknowledgment, and current-head completion. This is conditional troubleshooting, not a universal review gate.
- Before the first push or review request, preflight each touched area against its closest local style and test guidance plus nearby sibling precedent. Apply [Organization Before Authoring](../hands-off-agentic-coding/workflow.md#organization-before-authoring) to trace materially changed ownership and data flow and review the author's boundary decisions. Check only touched files for conventions a formatter may miss—import grouping, blank-line separation, test hierarchy, naming, and focused assertions—then run the repository formatter/checker. Formatter output is not proof of local structural compliance.
- For production import boundaries, use [Project-Root Imports and Paths](../../docs/references/code-organization-reference.md#project-root-imports-and-paths). For Vue component naming and template-ref consistency across analogous in-scope components, structure/root types, form-owned dependent-field watchers, loading/disabled state, stock UI reuse, and scoped utility-style presentation, use the [Vue Component Authoring Reference](../../docs/references/vue-component-authoring-reference.md).
- Require working project-appropriate linting and current passing command evidence using [Project Linting Verification](../../docs/references/rules-and-verifications-reference.md#project-linting-verification). Reuse the documented wrapper and configured warning policy; inspect coverage for the changed languages rather than treating formatter/typecheck success as lint evidence.
- For changed style declarations, follow [CSS Diagnostics for Style Changes](#css-diagnostics-for-style-changes); unrelated changes do not activate CSS-only checks.
- In MJML templates, prefer supported native styling mechanisms over an HTML wrapper added solely for CSS. Use supported direct attributes where available; where a component such as `mj-text` lacks the required attribute, use `css-class` with rules in `mj-style inline="inline"`. Do not invent unsupported attributes or remove structurally necessary wrappers. Run the project's strict MJML validation/compilation, inspect generated inline CSS and preserved content, and verify the relevant rendered behavior. Use [Compiled MJML Output](#compiled-mjml-output) for ending-component and delivered-HTML boundaries.
- For coupled interaction changes or corrective UX feedback across related gestures, use [Interaction Contract Activation](../outcome-first-planning/workflow.md#interaction-contract-activation) before the next gesture patch. Keep the fit check scoped to the relevant contract; isolated wording or mechanical changes do not need it.
- When custom code replaces or intercepts a library's interaction lifecycle, use that same interaction-contract check to preserve affected supported input sensors through begin/move/release/cancel. Do not accept native DOM drop handling or mouse-only tests as proof of touch/fallback parity; keep normalization at the sensor boundary and reuse existing domain target/commit rules.
- Prefer deletion and simpler existing patterns over new abstractions. Apply [Human Readability](../../docs/references/code-organization-reference.md#human-readability)'s per-file cleanup eligibility rule; after an accepted scope correction, inspect the complete in-scope PR for equivalent incidental-only files.
- After feature deferral or simplification, use [Simplification After Scope Changes](../../docs/references/code-organization-reference.md#simplification-after-scope-changes): restore the original simple shape when supporting abstractions are no longer needed, remove static reactive wrappers only when the consumer supports plain values, and retain refactors required by accepted work.
- For generic parsing, traversal, tokenization, serialization, or equivalent plumbing, apply [Libraries for Generic Mechanism](../../docs/references/code-organization-reference.md#libraries-for-generic-mechanism): inspect existing frontend/backend library choices before adding an overlapping dependency, then compare standard-library, installed, maintained-library, and bespoke options. Prefer lower net owned complexity while preserving runtime compatibility and explicit security policy; sharing a library does not require identical configuration.
- For queued or deferred work, inspect whether its payload references a record the initiating operation deletes or invalidates before execution. Pass immutable delivery fields as a snapshot when they are sufficient; reload live state only when current data is required and absence is handled deliberately. Request a focused delayed-execution or deletion-path check when this lifecycle applies. For persisted argument changes, apply [Durable Job Payload Changes](../../docs/references/code-organization-reference.md#durable-job-payload-changes) to type, position, arity, and representation; prove prior payload readability or a verified cutover, not just fresh-producer success.
- For migrations that split or rename persisted settings, map every target setting to its semantically corresponding legacy source before selecting defaults. Preserve existing explicit choices, including opt-outs; use current defaults only when no source setting exists. Request a focused backfill test or data assertion for both an existing opt-out and a missing legacy preference.
- Review migration ownership, order, dialect operations, helper placement, and disposable implementation checks against [Self-Contained Migrations](../../docs/references/code-organization-reference.md#self-contained-migrations). Retain check outcomes before removing migration-only checks and dedicated fixtures prior to commit; keep application tests, shared fixtures, and required recovery/audit artifacts. Preserve local definitions, dependency/rollback order, and justified raw SQL; do not rewrite released history or impose a file quota. Review application text rules under [Text Validation Ownership](../../docs/references/code-organization-reference.md#text-validation-ownership) and policy-to-service payload typing under [Express Light Rail](../express-light-rail/workflow.md#intent).
- For new backfills, apply [Best-Effort Backfills](../../docs/references/code-organization-reference.md#best-effort-backfills): tolerate explicitly identified unusable legacy inputs only within the project's preservation contract, retain usable neighbors, and propagate genuine database failures. Require focused valid/malformed/valid and database-failure evidence; verify accepted loss/recovery before source removal, rather than prescribing deletion or rewriting released migrations.
- For frontend request aggregation, use [Keyed Frontend Request Coalescing](../../docs/references/engineering-techniques-reference.md#keyed-frontend-request-coalescing) to review canonical keys, result ownership, invalidation, and cancellation separately.
- For expected-JSON consumers and error recovery, apply [Intermediary Responses to JSON Requests](../../docs/references/engineering-techniques-reference.md#intermediary-responses-to-json-requests): review marked/unmarked HTML on successful and rejected responses, ordinary JSON/non-JSON contracts, loaded-state and uncertain-write safety, framework propagation, listener teardown, and optional-preview trust.
- When a review finds a dependency capability gap, use [Evidence-Backed Upstream Limitations](../../docs/references/engineering-techniques-reference.md#evidence-backed-upstream-limitations) before suggesting private patches or duplicate upstream issues.
- Review development wrappers against [Thin Entry Points and Values](../../docs/references/dev-tooling-portability-reference.md#thin-entry-points-and-values): reject unnecessary compatibility parsing, fallback startup, and duplicated environment/configuration helpers while preserving real prerequisite, integration, and lifecycle invariants. Apply [Dependency Release Selection](../../docs/references/dev-tooling-portability-reference.md#dependency-release-selection) when choosing an adopted release instead of copying a sibling's incidental pin.
- For validation catalogs and argument preflight, apply [Ownership and Control-Boundary Checks](../../docs/references/dev-tooling-portability-reference.md#ownership-and-control-boundary-checks): derive ownership from its existing execution/config source, keep help-like child argv opaque, and request a real spawned-child proof without inventing override features.
- Prefer explicit branching or guards over ternaries when control flow reads more clearly; do not extract wrappers solely to remove ternary syntax. For service inputs, query naming/scopes, comments, preload contracts, CRUD/index naming, field policies, and semantically safe emptiness checks, use the bounded guidance in [Code Organization Reference](../../docs/references/code-organization-reference.md).

- Do not block on project-specific rules that are not documented locally.
- Test expectations should be declarative expected data, not expectation-building logic. For business catalogs and configured defaults, prefer explicit expected values over mapping, sorting, branching, or deriving expectations from the same production constant/helper under test.
- Assert fetched/returned collections directly rather than projecting actual values inside `expect`; preserve native async and matcher APIs. Do not add sorting solely to normalize assertions or assume unordered SQL guarantees operation sequence. Distinguish raw fixture `...Attributes` collections from persisted records, including table-driven fields and consumers. Follow [Scenario-Oriented Verification](../../docs/references/code-organization-reference.md#scenario-oriented-verification) and compliant project siblings.
- Put queries used only to observe persisted results in Assert beside their expectations. Use the normal model API for routine ORM-backed observations, retaining specialized SQL where concrete database semantics require it. Prefer a simple awaited query over unnecessary post-query filtering only when fixture isolation makes it equivalent; preserve needed constraints/options and keep the actual operation in Act. Follow [Scenario-Oriented Verification](../../docs/references/code-organization-reference.md#scenario-oriented-verification).
- Keep each test focused on one observable contract, not a numeric assertion quota. HTTP status and body together describe one HTTP result: prefer a native or meaningful matcher such as [`toHaveHttpResponse`](../../docs/references/http-response-matcher-reference.md) rather than a fabricated wrapper object. Where no suitable matcher is available, preserve legitimate project-standard direct status/body assertions as one coupled result. Do not add inline verifier-waiver/justification comments, equivalent rationale prose, broader suppressions, assertion bundles, or weaker assertions to evade a count rule; report a conflicting local syntax policy truthfully. Keep independent persistence effects separate. A real returned object or array remains a valid direct assertion target. Preserve web-first browser matchers and native promise-error assertions such as `await expect(promise).rejects.toThrow(...)`; do not manually catch its rejection or aggregate it with mock-call arrays. Assert mock calls only when independently observable and important, in their own focused test. Multiple assertions remain appropriate when they jointly prove one coupled invariant. Repository-native assertion patterns override generic guidance. See [Assertion Quality Requires Review](../../docs/references/test-alignment-verifier-reference.md#assertion-quality-requires-review) for examples and the verifier's limits.
- For changed JavaScript/TypeScript test files, read the inherited [Shared Baseline](../../docs/references/test-alignment-verifier-reference.md#shared-baseline) before the first push or review, alongside the nearest test-directory README and local test guidance. Apply its naming and phase requirements to every test in each changed file, not only edited callbacks; retain explicit local additions and supported scoped suppressions. Report local assertion conventions and flag violations before reporting `PASS`, including multiple `expect(...)` calls when the local standard allows only one. Do not treat assertion count by itself as test quality. Before merge, obtain the applicable declared check's current-scope result using [Diff Scope](../../docs/references/test-alignment-verifier-reference.md#diff-scope); a passing behavioral suite or anticipated final-yield advice is not that evidence. For semantic assertion quality, use the declared [Test Assertion Focus check](../../docs/references/test-alignment-verifier-reference.md#semantic-assertion-focus-check) in addition to the structural test-alignment check.
- When the user designates another project as testing precedent, inspect that reference before test edits and reuse its applicable harness and assertions. Follow [Scenario-Oriented Verification](../../docs/references/code-organization-reference.md#scenario-oriented-verification); do not replace the designated pattern with an unexamined custom renderer or parser.
- For dependency-related tests and cutovers, apply [Scenario-Oriented Verification](../../docs/references/code-organization-reference.md#scenario-oriented-verification) to distinguish upstream API behavior from application-owned invariants, observed integration regressions, and already-covered consumers before recommending additions or deletions.
- For component tests, apply [Scenario-Oriented Verification](../../docs/references/code-organization-reference.md#scenario-oriented-verification) to visible application outcomes, scenario-local mount/response setup, typed frontend factories, and readable assertion targets. Check source/test ownership under [Domain-Oriented Modules and Tests](../../docs/references/code-organization-reference.md#domain-oriented-modules-and-tests); preserve legitimate infrastructure and integration assertions without extraction quotas.
- For permanent test intent and setup, apply [Scenario-Oriented Verification](../../docs/references/code-organization-reference.md#scenario-oriented-verification): use factories rather than unrelated production-service setup, retaining subject-service and feature-test calls; test the current interaction instead of memorializing a retired control's absence. Preserve legitimate negative contracts and keep investigative probes disposable.
- Pair positive application-boundary coverage with a meaningful rejected/excluded control under [Scenario-Oriented Verification](../../docs/references/code-organization-reference.md#scenario-oriented-verification). Check that it exposes wrong fixtures or missing filtering/authorization; reuse existing boundary coverage instead of adding unrelated cases or quota-driven duplicates.
- For CLI/API adapter doubles, review whether consumed options, fields, response shape, and semantics match the supported external interface; use [External CLI and API Doubles](../testing-instructions/workflow.md#external-cli-and-api-doubles) for focused fixtures and safe boundary smoke decisions.
- For tooling verification, review whether an appropriate established suite exists before accepting a new permanent runner; for one-off no-suite checks, prefer disposable behavioral smoke evidence. See [Hands-Off Agentic Coding](../hands-off-agentic-coding/workflow.md#intent) for the scope boundary and permitted permanent regression/infrastructure work.
- Keep persisted scenario creation explicit in each test's Arrange section, even for identical records; flag persistence hidden in shared `beforeEach` hooks. Preserve legitimate environment hooks and opt-in named factory traits. Keep descriptive fixture-backed test function names, inspect configured runner cleanup before adding redundant local hooks, and retain uncovered-resource cleanup or intentional mid-test restoration. Follow [Scenario-Oriented Verification](../../docs/references/code-organization-reference.md#scenario-oriented-verification) and [Cleanup Necessity](../../docs/references/code-organization-reference.md#cleanup-necessity).
- Before adding a shared setup or teardown hook that awaits an external, asynchronous, or potentially slow subsystem, assess its fan-out under the configured runner: a global `beforeEach` or equivalent multiplies waits, retries, polling, or cleanup by every test and worker. Keep the hook in the narrowest suite or describe block whose tests observe the asynchronous invariant unless every test needs it. Preserve a focused regression for the race or lifecycle hazard. Reviewers should reject global asynchronous cleanup without an all-suite correctness reason or measured fan-out rationale; this does not constrain normal in-memory setup or impose timing budgets.
- Before retaining or moving test cleanup, identify the live resource, isolation requirement, or observable invariant that needs it. Remove unnecessary settlement of intentionally pending in-memory mock promises rather than moving it into `finally` or a hook for body shape; do not resolve early, snapshot, or weaken a pending-state assertion. Reuse automatic teardown. Keep explicit disposal for live timers, I/O, subscriptions, disposal-under-test, or demonstrated isolation needs; see [Cleanup Necessity](../../docs/references/code-organization-reference.md#cleanup-necessity) for examples.
- Check [Cleanup Necessity](../../docs/references/code-organization-reference.md#cleanup-necessity) for invariant wrapper teardown: register it once in runner-loaded shared setup, migrate duplicate per-file registrations together, and place setup registrations before teardown registrations for source readability—not as a claim about changing runner phases. Preserve disposal-under-test and uncovered cleanup.
- For generated or touched JavaScript/TypeScript, allow short clear one-line guards with a blank line afterward; consecutive short guards may be adjacent with a blank line only after the last. Keep non-short guards multiline and braced; do not compress every guard. Prefer `isUndefined` only when Lodash is already available and undefined-only semantics fit; preserve safe `typeof` checks, nil semantics, local/user precedence, and do not add dependencies. For exceptional error responses, use an explicit early return and keep the ordinary error response as the normal path. Elsewhere, prefer explicit branching when clearer; a concise scalar ternary may remain when genuinely clearest. See [Guard Clauses and Exceptional Responses](../../docs/references/code-organization-reference.md#guard-clauses-and-exceptional-responses).
- Make readability an explicit delivery gate: before reporting `PASS`, name each independent responsibility and its side effects. Flag unstructured accumulation of independent scenarios or repeated mechanics that hides the contract; review structure rather than numeric readability proxies, preserve literal scenario data locally, and do not require mechanical splits or generic fixture builders. Use the scenario guidance in [`../../docs/references/code-organization-reference.md`](../../docs/references/code-organization-reference.md) when reviewing verification code.
- For input-heavy utility tests, selectively consider reproducible property-based or metamorphic checks; use the bounded mutation spot-check only when test sensitivity is uncertain. Follow [Input-Heavy Utility Tests](../../docs/references/code-organization-reference.md#input-heavy-utility-tests) and [Bounded Mutation Spot-Checks](../../docs/references/code-organization-reference.md#bounded-mutation-spot-checks), not exhaustive business matrices or numeric quality gates.
- When modeling mutually exclusive states, consider a discriminated union rather than independent flags; see [Tagged Unions for Exclusive States](../../docs/references/code-organization-reference.md#tagged-unions-for-exclusive-states). Do not replace runtime validation at untrusted boundaries.
- For each changed barrel or `index.ts`, preserve existing semantic export groups and comments; keep namespace imports, named exports, and default-export object keys alphabetized by exported symbol within each group. Flag out-of-order members as required corrections and do not require unrelated barrel-file rewrites. For test dependency bundle imports versus direct full-module subject imports, use [Project-Root Imports and Paths](../../docs/references/code-organization-reference.md#project-root-imports-and-paths). For service-specific group order and labels, use [Service Orchestration Readability](../../docs/references/code-organization-reference.md#service-orchestration-readability).
- Review commit scope when relevant: flag mixed code/test changes, migrations/schema/data changes, dependency churn, formatting, and documentation or workflow-learning updates unless the user explicitly requested a combined commit and the files are inseparable for review.
- For maintainability or organization findings, use the packaged `../../docs/references/code-organization-reference.md` reference when no local equivalent exists: flag boundaries, modules, helpers, or abstractions only when they affect ownership, data handoffs, dependency direction, side effects, or future change safety. Keep complexity checks separate from ownership and safety findings.

- Before proposing a reorganization, run the domain-discovery checkpoint in [`../../docs/references/code-organization-reference.md`](../../docs/references/code-organization-reference.md): inspect topology, cohesive concepts, repeated change clusters, varying dispatch dimensions, owned invariants, dependency direction, and sibling conventions. Treat churn, growing branches, context-heavy helpers, and repeated boundary crossings as evidence to investigate—not proof of a new abstraction—and record each candidate's evidence, responsibilities, boundary, and smallest safe next action.
- Flag private helpers that read instance fields when a caller can pass those values explicitly. Do not force parameters when the helper is inherently bound to object state. For service classes, apply the conventions linked above: constructor-backed action inputs stay in `perform`, developer preload guards precede side effects, and returned instances preserve caller preload graphs.

## Documentation Purpose and Placement

For changed documentation, read the applicable ordinary-language project rules and identify the intended reader question, purpose, placement, and existing authoritative owner. Apply [Selecting Documentation Content](../../docs/workflows/project-knowledge-base-workflow.md#selecting-documentation-content); assess the passage's content, not just its pathname.

Source-directory READMEs may teach when and why to use a layer or pattern, how to author within it, and its boundaries, with small usage examples. Flag passages that merely inventory implementation behavior or repeat another layer's instructions. Identify the affected passage, governing rule, and concrete correction: explain the authoring decision, link to the existing owner, or retain implementation-local rationale beside code. Use the knowledge base for an actual durable domain or architecture question, not as a destination for displaced implementation summaries. Do not ban source READMEs or force new documentation when an existing owner already answers the question.

Compare material documentation claims with current implementation and supported configuration, including execution order, parallel prerequisites, retries versus reruns, partial failure, and the meaning of success when relevant. Recover referenced implementation and existing owner documents into the semantic request before assessment; unavailable required evidence is `BLOCKED`, not approval based on formatting, links, or author assertions.

The supplied `marlens-rules:documentation-purpose-alignment` contract selects changed root/nested Markdown and MDX through OMP Verifier. Assess the complete changed passages and governing guidance with cited whole-scope results; a clean subsection or empty selection does not establish semantic coverage. The provider supplies policy, while Verifier owns capture, evaluation, and native blocker delivery; this contract does not add a hard completion veto or unattended reassessment.

For main README capability and usage claims, apply the [released-artifact boundary](../release-notes/workflow.md#shared-release-history-default). An `Unreleased` label does not make a source-only capability preview appropriate in the main README.

Report documentation-purpose coverage separately from formatting, link validity, behavioral tests, and code-module verification; none proves the others. If the required rules or source are unavailable, name the missing prerequisite rather than claiming semantic coverage. Exercise the contrasting [documentation-purpose examples](../../examples/documentation-purpose-review.md) when verifying this review path.

## CSS Diagnostics for Style Changes

When style declarations change, inspect the project's configured CSS diagnostic provider for the changed standalone CSS files and supported embedded Vue `<style>` blocks, in addition to formatting, type checks, and rendered behavior. A Vue script/template-only change or another unrelated change does not acquire CSS-only verification work.

`css(vendorPrefix)` identifies a CSS language-service diagnostic. Establish coverage from the project's actual linter/parser/plugin/provider configuration and output: ESLint can support additional languages through suitable integrations, but a script-only ESLint, type-check, or browser PASS does not establish that CSS diagnostics are clear. Add supported standard equivalents where appropriate while retaining browser-required vendor-prefixed fallbacks; for example, supported `line-clamp: 3` can accompany `-webkit-line-clamp: 3`. Do not require an unprefixed twin for every prefixed property.

Reuse project-configured tooling and respect its supported syntax, dialects, custom CSS data, and settings; validate embedded style blocks with their supported service rather than parsing the entire Vue file as CSS. Report unavailable required diagnostic coverage as `BLOCKED` with the missing provider or block/dialect support. Do not silently add project dependencies, weaken checks, or substitute rendered behavior for diagnostic evidence.

## Compiled MJML Output

MJML ending components such as `mj-text` can treat their contents as HTML. Nesting another MJML component there, such as `mj-raw`, does not guarantee it is compiled away; strict compilation and a plausible browser preview can still leave literal component elements in delivered HTML. Validate the supported hierarchy and prefer direct interpolation of already-sanitized HTML where supported. Preserve escaping, sanitization, and structurally necessary wrappers.

Inspect the resulting DOM at the affected boundary for leaked component elements while preserving intended paragraph breaks, formatting, links, and inline whitespace styles. Distinguish actual elements from escaped user-visible text; do not add a blanket substring verifier or ban all wrappers. Keep strict-compilation, browser-preview, and actual email-client compatibility evidence separate; none alone proves the others.

## Process

1. Read the request, issue, PR body, or plan.
2. Inspect the changed files and identify whether the change is backend, frontend, migration, test-only, documentation-only, or cross-cutting.
3. Read project-local rules and setup docs that govern the changed area.
   For documentation changes, perform [Documentation Purpose and Placement](#documentation-purpose-and-placement) before reporting review completion.
4. Check behavior and contracts: API shapes, serializers, policy/access rules, migrations, persistence, and UI route flows when relevant. Apply [Invariant-Preserving Mutations](../../docs/references/code-organization-reference.md#invariant-preserving-mutations): ordinary operations preserve their invariant and unrelated valid state rather than invoking general repair; retain explicitly required repair/migration work.
5. Check type and error handling: avoid unsafe casts, non-null assumptions, swallowed errors, and impossible states represented as runtime branches. Apply [Error Ownership and Local Recovery](../../docs/references/code-organization-reference.md#error-ownership-and-local-recovery) for transport/UI separation, positive local handling, application error hierarchies, and operation-specific structured logs.
6. Check tests and verification: changed behavior should have the smallest meaningful runnable check, and PR testing instructions should match user-visible behavior.
7. Report evidence-sensitive checks as `PASS`, `FAIL`, or `BLOCKED` using the shared vocabulary in `AGENT_RULES.md`.
8. Check code organization: flag modules, services, repositories, value objects, adapters, or helper extractions that obscure ownership, create cycles, pass context bags, hide side effects, or fail to group code that changes together. Treat an oversized file as a signal to inspect responsibility clusters, independent change axes, side effects, dependency direction, and extraction seams; do not require a split when the file is cohesive, and do not accept a mechanical split that preserves the same tangles. State names should describe represented domain facts or lifecycles, and query/composable results should stay beside their direct derived state unless a stronger local convention applies.
9. Check simplicity: flag helpers, options, abstractions, comments, or compatibility paths that solve no current problem. Apply [Default-Safe Lifecycle APIs](../../docs/references/code-organization-reference.md#default-safe-lifecycle-apis) when ordinary safety is opt-in or implementation bookkeeping leaks into a framework-like caller interface.
10. Check dead code: if a replacement makes old code unreachable, remove stale types, imports, exports, and documentation.

## Optional Selected-File PR Review and Viewed State

Use this mode when the request names a pull request and one or more repository-relative changed paths. Confirm the GitHub API identity is the intended account. Reuse the review process above, inspecting enough PR/base, relevant source, caller/test, and project-local context for each selected file; record the exact reviewed `headRefOid` and focused verification.

Only when explicitly requested, mark a selected file viewed if it has no finding and sufficient review evidence. Do not mark files with findings, missing relevant context, unresolved verification, or absent exact paths. Follow [Pull Request File Viewed State](../../docs/references/github-tooling-reference.md#pull-request-file-viewed-state): require the current head to match the reviewed OID immediately before the mutation, then freshly read back both the head and exact file's viewed state. Claim success only for a matching head and `VIEWED`; changed heads require fresh review, not a stale success claim. These checks are not an atomic revision-conditioned mutation.

Report selected paths, reviewed revision, findings or verification limits, and observed viewed state. Keep mutation/readback failures separate from review conclusions. Viewed state records personal progress, not PR approval or merge readiness; this mode does not authorize source edits, commits, pushes, approval, merge, or marking unrelated files.

## Output Contract

List findings first, ordered by severity.

```text
[severity] Short finding title
File: path/to/file.ts:42
Risk: What can break or mislead users/developers.
Fix: One concrete change.
```

After findings, include open questions or assumptions. If there are no findings, say that clearly and mention any test gaps or residual risk.
